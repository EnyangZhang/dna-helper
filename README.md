# DNA Helper

DNA Helper 是基于 [MaaFramework](https://github.com/MaaXYZ/MaaFramework) 和 MXU 的《二重螺旋》Windows 自动化助手。当前提供 8 个用户任务、共 10 种游戏运行模式：

- 密函无尽加速：无尽、驱离。
- 普通无尽加速：扼守、无尽、驱离。
- 皎皎币挂机：从指定委托页启动，校验局内小地图后自动完成 99 局副本循环。
- 调停挂机：可从结算页、弹窗 Space“开始挑战”页面或已进入的副本接管，确认局内后执行固定的 W、左键、四次 F、鼠标上移、右键蓄力与 Z 操作，并按结算页自动循环副本。
- 狩月人之阶挂机：可从结算页或已进入的活动副本接管，确认局内后执行三次左键蓄力与 Q 起手并持续按 E，识别“重新开始”后停止输入并按设定轮次直接重开。
- 钓鱼挂机：设定目标数量后，在大世界钓鱼地点识别鱼竿、收鱼和关闭提示，分别发送 Space、E、Esc，达到目标后自动结束。
- 沉浸式戏剧挂机：首次手动入场，确认血条后执行 W/D/F/Q 起手；可选持续 E 或不持续 E 的伊薇方案；不持续 E 方案按场景 2/3/4 中心横幅、场景 5 顶部 Boss 条各一次等待 3000ms 并左键长按 300ms，识别“前往”后快速点击并等待下一副本。
- 进度监控：可独立持续运行并由 UI 手动停止；排在游戏任务前时自动作为一次性 Telegram 启动器。

任务通过图像识别确认当前页面，再执行鼠标或键盘输入。所有模板、ROI 和固定坐标均按 `1280×720` 基准画面制作。

## 从 GitHub 首次安装到运行

下面是新 Windows 电脑从克隆仓库到双击 DNA Helper 图标的完整流程。仓库不会提交 `dist/`、`.cache/` 或编译后的 EXE，因此首次克隆后必须在本机完成一次构建。

### 第 1 步：安装一次性构建环境

需要安装：

- [Git for Windows](https://git-scm.com/download/win)。
- 64 位 Python 3.9–3.12；建议 Python 3.11。安装时必须让 `python` 可从 PATH 调用，参见 [Python Windows 官方说明](https://docs.python.org/3/using/windows.html)。
- [Node.js 22 LTS](https://nodejs.org/en/download) 或更新的 LTS 版本。
- pnpm 10.28.0。
- [Rust stable MSVC](https://v2.tauri.app/start/prerequisites/#rust)。
- [Microsoft C++ Build Tools](https://v2.tauri.app/start/prerequisites/#microsoft-c-build-tools)，安装器中勾选“使用 C++ 的桌面开发”。
- Microsoft Edge WebView2。Windows 10 1803 及更高版本通常已经安装；如果程序窗口空白，再安装 [WebView2 Evergreen Runtime](https://developer.microsoft.com/microsoft-edge/webview2/)。

可以先在 PowerShell 中用 `winget` 安装 Git、Python、Node.js 和 Rust：

```powershell
winget install --id Git.Git -e
winget install --id Python.Python.3.11 -e
winget install --id OpenJS.NodeJS.LTS -e
winget install --id Rustlang.Rustup -e
```

Microsoft C++ Build Tools 建议按上面的 Tauri 官方链接手动安装并确认勾选“使用 C++ 的桌面开发”。安装完所有工具后，关闭并重新打开 PowerShell，然后执行：

```powershell
rustup default stable-msvc
npm install --global pnpm@10.28.0
```

确认环境：

```powershell
git --version
python --version
node --version
pnpm --version
rustc --version
cargo --version
```

要求：

- `python` 应显示 3.9–3.12。
- `node` 应显示 22 或更新的 LTS 版本。
- `pnpm` 应显示 10.28.0。
- `rustc` 和 `cargo` 必须可运行。

如果刚安装后命令仍找不到，重启 PowerShell；仍无效时重启 Windows。

### 第 2 步：克隆仓库

以下示例将项目放在 `D:\Projects\dna-helper`；也可以换成自己的目录：

```powershell
New-Item -ItemType Directory -Force D:\Projects | Out-Null
Set-Location D:\Projects
git clone https://github.com/EnyangZhang/dna-helper.git
Set-Location .\dna-helper
```

如果已经配置 GitHub SSH 密钥，也可以使用：

```powershell
git clone git@github.com:EnyangZhang/dna-helper.git
```

后续所有命令都必须在刚克隆的 `dna-helper` 项目目录中执行。

### 第 3 步：安装 DNA Helper 的 Python 运行依赖

```powershell
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
python -c "import maa; print('MaaFramework Python Agent：正常')"
```

首次使用不建议只把依赖安装进 `.venv`。桌面版从资源配置中执行的是系统 PATH 里的 `python agent/main.py`；如果 `maa` 只存在于虚拟环境，双击 EXE 后 Agent 会启动失败，角色技能、焦点恢复和轮次日志将不可用。

### 第 4 步：先校验项目

```powershell
python tools\validate_project.py
python -m compileall -q agent tools
python -m unittest discover -s tests -v
```

正常结果应包含类似：

```text
OK: 1 controller(s), 2 group(s), 3 task(s), 2 preset(s), 121 reachable pipeline node(s), 9 template(s)
```

### 第 5 步：首次编译定制 MXU

DNA Helper 使用带安全日志清理功能的定制 MXU。执行：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\tools\build_custom_mxu.ps1
```

该脚本会：

1. 把固定的 MXU v2.1.3 源码克隆到 `.cache/mxu-v2.1.3/`。
2. 校验固定基线提交并应用 `tools/mxu-v2.1.3-log-retention.patch`。
3. 安装前端和 Rust 依赖。
4. 生成定制 `mxu.exe`。

第一次会下载和编译大量依赖，耗时较长属于正常现象。完成时应显示：

```text
Custom MXU built: ...\mxu.exe
```

常见失败：

- `pnpm` 或 Vite 报 Node 版本过旧：安装 Node.js 22 LTS，重开 PowerShell。
- 找不到 `link.exe`、Windows SDK 或 MSVC：重新打开 Visual Studio Installer，安装“使用 C++ 的桌面开发”；必要时在“Developer PowerShell for VS 2022”中重新执行构建命令。
- 找不到 `cargo` / `rustc`：执行 `rustup default stable-msvc` 后重开终端。

### 第 6 步：组装 DNA Helper 桌面目录

确保 DNA Helper 没有在运行，然后执行：

```powershell
python build_ui.py
```

成功时会显示：

```text
构建完成：...\dist\DNAHelper\DNAHelper.exe
```

确认图标已生成：

```powershell
Test-Path .\dist\DNAHelper\DNAHelper.exe
```

结果应为 `True`。

`build_ui.py` 只接受已经构建的定制 MXU，不会退回缺少日志清理功能的官方二进制。它会复制 MaaFramework、项目资源和 Python Agent，并在以后重建时保留 `dist/DNAHelper/config/` 和 `dist/DNAHelper/debug/`。

构建并非事务式操作。程序未退出或 DLL 被占用时可能留下不完整输出；发生失败后先退出 DNA Helper，再重新执行 `python build_ui.py`，不要继续运行半成品。

### 第 7 步：创建桌面图标

打开项目中的：

```text
dist\DNAHelper\DNAHelper.exe
```

推荐创建桌面快捷方式：

1. 右键 `DNAHelper.exe`。
2. Windows 11 选择“显示更多选项”。
3. 选择“发送到 → 桌面快捷方式”。
4. 右键桌面上的 DNA Helper 快捷方式，打开“属性 → 快捷方式 → 高级”。
5. 勾选“用管理员身份运行”。

以后双击这个桌面图标即可启动，不需要再次打开 PowerShell。

DNA Helper 使用单实例桌面壳。窗口因点击 `X` 隐藏到系统托盘后，再次双击 `DNAHelper.exe` 或其快捷方式，只会显示、还原并聚焦已经运行的主窗口，不会创建第二个 UI、托盘图标或 Agent。

### 第 8 步：第一次连接游戏并开始任务

1. 先启动《二重螺旋》。
2. 将游戏设为项目使用的 `1280×720` 窗口基准。桌面版目前不会自动拒绝错误尺寸。
3. 双击桌面 DNA Helper 图标，并同意管理员权限提示。
4. 首次启动会自动创建两个独立标签页：
   - “密函挂机”：先执行“进度监控”，再执行“密函无尽加速”。
   - “普通挂机”：先执行“进度监控”，再执行“普通无尽加速”；同时带有默认不启用的“调停挂机”“狩月人之阶挂机”和“沉浸式戏剧挂机”，需要运行时只启用一个长期游戏任务。
5. 点击本次要运行的标签页。不要同时启动两个长期任务。
6. 打开右侧“连接设置”，选择“二重螺旋（前台控制）”和“基础资源”。
7. 选择标题为“二重螺旋”的游戏窗口并点击“连接”。MXU 能自动匹配时，也可能直接显示“已连接”。
8. 在任务卡片中选择模式、轮次和技能选项。
9. 让游戏停在对应副本或可识别页面，然后点击“开始任务”，也可以按 `F10`。
10. 需要停止时点击“停止任务”或按 `F11`。如果仍收到旧的手机消息，可在 Telegram 发送 `disconnect`；若监听已不能接收命令，在“设置 → 调试”使用“关闭监听并清理残留进程”。

两个标签页彼此独立，避免把两个长期游戏任务排进同一队列后由第一个任务永久阻塞第二个。“进度监控”会读取 MXU 已完成的本轮任务提交记录；确认后面还有游戏任务时自动作为一次性启动器，因此启动监听后立即让位给游戏任务。

控制器使用真实前台鼠标键盘输入。每组点击或按键结束后 Agent 会尝试切回原窗口，但 Windows 可能拒绝恢复；运行时不要依赖焦点一定能够成功切回。

### 以后每天如何启动

首次构建完成后，日常使用只需：

1. 启动《二重螺旋》，保持 `1280×720` 窗口基准。
2. 双击桌面的 DNA Helper 快捷方式，以管理员身份启动。
3. 选择之前保存的配置。
4. 确认游戏窗口已连接。
5. 点击“开始任务”或按 `F10`。

不需要每天重新克隆、安装依赖或编译。

## 日志清理

程序启动时会自动删除 `dist/DNAHelper/debug` 内修改时间超过 14 天的普通文件，并删除清理后留下的空目录。

“设置 → 常规 → 自动清理运行日志”下方提供红色“完全清空日志”操作项。确认后程序会安排重启，并在新日志创建前清空该目录；重启后的当前日志会保留。

所有清理都会解析并核验目标，只允许操作可执行文件同级的真实 `debug` 目录。遇到符号链接、Windows 重解析点、非普通文件或越界路径时会拒绝整次操作。

## 关闭监听与本地残留进程清理

Telegram 的 `disconnect` 保持原有行为：正常监听收到命令后发布跨进程停止信号并停止自身通讯，不扫描或终止任何进程。信号检查线程正常的同目录 Agent 通常约 2 秒内停止接收、发送、30 分钟定时状态和监听权线程；若残留进程只发送、不再接收，手机命令无法保证触达。

“设置 → 调试”的红色按钮改为“关闭监听并清理残留进程”。确认后既发布原有通讯停止信号，又在后台扫描系统全部进程；只对当前助手目录 `config/agent-processes` 中登记的 Python Agent 进行清理资格核验。PID、Windows FILETIME 创建时间和解析后的程序路径必须全部匹配，且原父进程已退出（或父 PID 已被更新的进程复用），才直接终止该残留 Agent，并等待确认退出。这个本地操作不依赖旧 Agent 的 Telegram 接收线程或信号守护线程，所以兼容已有登记的旧版残留。

仍有正常父进程的 Agent 会保留，只收到原有通讯停止信号；不会为强制关闭通讯而中断当前游戏任务。身份不明、权限不足或路径异常的项会跳过并报告，绝不按 `python.exe` 名称批量结束。助手窗口、游戏、其他 Python、配置、日志及登记文件均不删除。扫描范围是整个系统，但终止授权仅覆盖本目录已登记的孤立 Agent，不自动扩大到其他安装目录。按钮结果显示扫描数、实际终止数、保留数、失效登记数；未核验项、失败 PID、扫描或信号发布错误会记录到日志并显示警告，不能将“信号已发布”宣称为“所有通讯已关闭”。之后停止并重新开始带“进度监控”的任务即可重新开启通讯。

停止信号固定写入解析后的 `<exe-root>/config/agent-processes/.monitor-disconnect.json`。程序拒绝符号链接、Windows 重解析点、非普通文件和越界路径，并通过同目录临时文件原子替换。每个新监听启动时先把现有信号记为基线，只响应之后产生的新代次，因此以前的 `disconnect` 不会误关将来重新启动的监控。升级后必须重启助手才能使用新的本地清理按钮；仍受正常 UI 管理的旧版 Agent 如果不响应信号，需要正常停止任务，不能冒险强杀。

## 任务说明

### 新功能的快速点击设计约束

以后新增或重构任何游戏功能时，凡是同一按钮需要连续点击 2 次及以上，都必须复用普通扼守的低延迟点击结构，不得在一次 Agent 自定义动作中用 `repeat` 循环完成多次点击：

1. 只有第一个节点负责图像识别；命中后立即执行一次 Maa 原生 `Click`。
2. 中间点击使用 `DirectHit + Click`，不重复识别同一张按钮模板。三连击时前两次点击的 `post_delay` 固定为 50ms。
3. 最后一次也必须使用 `DirectHit + Click`。Agent 禁止发送任何页面按钮点击，避免自定义动作的鼠标注入被游戏解释为角色攻击并改变站位。
4. 第三次原生点击后立即进入 `DirectHit + focus_guard_finalize` 收尾节点；该节点只恢复用户窗口和鼠标并记录逻辑事件，不向游戏发送输入。
5. 轮次、进度事件和“操作成功”日志只能绑定在收尾节点，每组连续物理点击只记录一次逻辑操作。
6. 收尾节点必须明确进入该按钮对应的下一状态；局内和局外识别仍遵守下文的分区，不得因为复用快速点击链而混用候选按钮。
7. 项目校验器必须覆盖新增点击链的坐标、节点顺序、50ms 间隔、原生第三击、无输入收尾和结束跳转，并全局拒绝基础 Pipeline 与任务覆盖中的 Agent 鼠标输入；构建桌面版后还要验证源码与 `dist/DNAHelper` 中的 Pipeline 一致。

如果某个游戏页面经实测必须使用不同点击次数或更长间隔，需要在对应功能说明中写明原因，并增加校验或测试固定该例外；不得无说明地退回 Agent 内部慢速循环。

调停挂机的固定局内角色操作允许 Agent 在确认游戏仍为前台后发送 Windows 物理相对鼠标移动和左/右键按下、抬起，但不得用它点击任何页面按钮。所有页面按钮仍必须使用 Maa 原生点击。

以后任何新功能只要涉及局内视角、瞄准或角色朝向的相对鼠标移动，默认必须复用已经实测有效的玩法鼠标方案：先确认游戏窗口仍在前台，再把总位移拆成连续的小步 Windows 物理鼠标事件，并在每步之间显式等待以控制移动速度。不得使用 Maa `post_relative_move`；控制器返回成功不能证明游戏输入层已经消费。只有对应功能经过明确的实机实验、文档约束和测试固定后，才允许使用独立的单次瞬时相对移动操作，不能静默改变通用分段移动的语义。当前唯一例外是调停挂机：一次性向上移动 130px 后等待 500ms。该规则只适用于局内玩法输入，页面按钮仍必须走 Maa 原生点击链。

### Pipeline 监控与过渡速度约束

以后新增或重构任何游戏功能时，不能依赖 MaaFramework 的节点默认时序。**每一个 Pipeline 节点都必须显式声明** `rate_limit`、`pre_delay` 和 `post_delay`；遗漏任意一个字段都会被项目校验器拒绝。默认值可能在按钮识别前引入约 200ms 的隐藏等待，即使后面的三连点击已经是 50ms 快速链，用户仍会感觉整个功能反应迟缓。

按节点职责使用以下标准：

1. 立即路由、页面过渡、状态门控、操作代理和完成决策使用 `rate_limit: 0`、`pre_delay: 0`、`post_delay: 0`。
2. 长期或边界未知轮询的空闲节点使用 `rate_limit: 0`、`pre_delay: 0`、`post_delay: 50`；50ms 是主动控制的轮询节流，不得再叠加框架默认延迟。
3. 连续 HUD 确认的前两帧使用 `0 / 0 / 50`，最后确认帧使用 `0 / 0 / 0`，因此稳定性只来自明确要求的帧数和 50ms 帧间隔。
4. 按钮候选必须按当前状态下最可能、最需要立即处理的顺序排列；快速轮询是同一状态机依次识别候选，不是真正并行线程。
5. 用户配置的技能等待、角色长按、识别时间窗等业务延迟可以非零，但三个字段仍必须全部写出，并在功能文档和校验或测试中固定其原因。皎皎币小地图识别窗口的 `rate_limit: 50` 属于这种明确例外。
6. 新功能交付前必须同时验证“按钮出现到第一次点击”的监控速度和“三次点击之间”的动作速度；只检查点击链不算完成。

当前密函、普通、皎皎币、调停、狩月人之阶、钓鱼、角色控制和进度监控的全部 Pipeline 节点均已显式声明这三个字段。校验器会全局检查字段完整性、非负数值以及既有三连点击结构，避免以后再次出现“点击链很快，但进入点击链之前很慢”的回归。

### 用户日志设计约束

所有功能的正常成功日志统一采用“结果型”写法：一个逻辑操作成功后最多记录一行，不再连续输出“识别到 → 准备操作 → 操作成功 → 返回监控”。页面按钮只记录实际点击成功，高台判断只记录最终分支，角色按键只记录实际发送结果；任务启动、真实轮次/进度、提前结算、错误地图、任务完成、输入失败、焦点异常和 Telegram 生命周期日志继续保留。

角色技能按以下方式记录：战斗 HUD 就绪只记录一次；高台与非高台各只记录一条判断结果；每次 E 仍单独记录 `第 N / 总次数`，以便核对连续点击是否完整；每组 Q 只在三次发送全部成功后记录一条 `3 / 3`；技能公共出口只表示“流程结束”，不能在 E/Q 全部关闭或非高台跳过 E 时误称技能已经释放。开启后台输入不会额外产生一组“准备发送 / 后台已发送”重复日志。

轮次日志仍以业务计数为准：普通扼守、普通驱离、密函驱离和皎皎币只在“再次进行”确认副本完成后记录一次；普通无尽和密函无尽只按真实局内进度记录。三连物理点击不得产生三条相同成功日志。项目校验器会拒绝同一节点配置多条正常焦点日志以及包含“准备”式过程描述的用户日志。

### 局内 / 局外识别分区

普通扼守、普通驱离、密函驱离和皎皎币挂机使用左下角角色血条作为**单向局内证据**。无论技能是否开启，连续 3 帧命中血条都能确认已经进入局内；血条消失只表示边界状态暂时未知，不能单独证明已经进入局外，因为释放 Q 等战斗表现可能临时隐藏 HUD。只有识别到该模式的局外专属按钮，才确认进入局外。血条边界检测与“是否释放技能”是两件事：技能关闭时仍用血条确认局内，但不会进入技能链。

同一状态中的多个候选按优先级快速轮询，这里的“并行检测”不是多个线程。正常局内业务监控只包含自己的局内按钮；进入边界未知等待后依次检查血条、该模式合法的局内按钮、局外专属按钮和空闲兜底。这样血条暂时消失后才出现的局内按钮仍能处理，同时普通驱离不会误接普通扼守的“继续挑战 / 确认选择”。已经由局外专属按钮确认的局外监控仍不识别局内按钮。

### 局内轮次与局外副本轮次

这两个“轮次”不是同一个计数：

- **局内轮次**：游戏在当前副本内部显示的关卡进度，例如普通扼守的第 1～99 局。有限副本在连续 3 帧血条确认入场时记为第 1 局，之后每次成功完成“继续挑战”才进入下一局；第 99 局即使没有下一次“继续挑战”，也会正确保留为 `99 / 99`。“确认选择”只负责页面推进，不单独加局内轮次。
- **局外副本轮次**：一个完整副本结束后累计的完成次数，也是 UI 中“副本轮次”选项控制的计数。只有局外识别到“再次进行”才加 1。

局外副本轮次适用于普通扼守、普通驱离、密函驱离、皎皎币挂机、调停挂机和狩月人之阶挂机；普通无尽与密函无尽不使用这个计数。普通扼守和皎皎币挂机当前范围为 1–999；普通驱离、密函驱离、调停挂机和狩月人之阶挂机范围均为 1–9999。今后新增或调整任何有限副本次数选项时，上限统一使用 9999，不再新增 999 上限。调停挂机和狩月人之阶挂机没有局内 99 轮计数，只显示已完成的局外副本轮次。

例如设置 2 轮：第一次出现“再次进行”时记录 `1 / 2` 并重开；第二次出现时记录 `2 / 2`，直接结束任务，不再点击“再次进行”。任务启动、进入局内、血条确认、技能释放、“继续挑战”、“确认选择”、“开始挑战”和 Space 确认都不会增加局外副本轮次。从“再次进行”页面启动任务时，该页面代表一个已经完成的副本，因此会正常计为一轮。

普通扼守或皎皎币挂机若在不足 `99 / 99` 时已经识别到“再次进行”，按“本次副本提前结算”处理：保留实际局内进度，不强制改写为 99，仍把该副本计入局外完成数；只要还未达到用户设置的副本总数，就继续重开下一次。开启进度监控时，每个提前结算的副本只向手机发送一次异常通知，例如 `第 3 / 10 次副本提前结束，实际局内进度 15 / 99，已计入完成并继续下一次。` 从“再次进行”页面接管且本次任务从未观察到局内血条时，仍计入完成，但不会伪造局内进度或误报提前结算。

### 密函无尽加速

#### 无尽

持续循环处理密函的三页流程：

“优先选择红色方块奖励”开关只在选择“无尽”模式时显示，默认关闭。关闭时恢复原来的直接确认流程；开启时才执行选卡识别，不强制所有无尽任务改选奖励。

1. 第一奖励页默认只识别“确认选择”，在 `(620,607)` 原生点击 3 次，不改选奖励。仅开启“优先选择红色方块奖励”后，才从左到右取第一个红色方块：第 1 张为红色时直接确认；否则选中第 2 或第 3 张最先命中的红色奖励，点击该卡后直接确认；没有红色时确认默认奖励。多个红色目标同样按最左优先，不再视为无目标。
2. 局内轮次页识别“继续挑战”，点击 `(900, 500)` 3 次。
3. 第三页识别“Space 确认选择”，点击 `(920, 480)` 3 次。

相邻点击间隔为 50ms。确认和继续按钮模板只包含稳定文字；选卡模板只包含红色方块本身，不包含数量、持有数、变化的场景或倒计时。

选卡使用独立的 `CipherRewardChoice.json` 和只读识别器 `agent/cipher_rewards.py`，仅“密函无尽加速 → 无尽”开启该选项时可达；密函驱离仍沿用原来的直接确认。不再识别标题或 I/II/III 编号，避免金色等稀有度外观变化阻断选卡。第 1 张是默认项，命中红色就直接确认，不检查勾选、不点击第 1 张；需要改选时，第 2、3 张坐标分别为 `(640,519)`、`(823,519)`。选卡与确认均为三次 Maa 原生鼠标点击：首节点识别，后两个 `DirectHit + Click`，间隔 `50 / 50ms`，第三次后通过无输入 `focus_guard_finalize` 恢复窗口和鼠标。第 2、3 张选卡三连击收尾后直接进入 `CipherEndlessRewardConfirmAfterSelect`，只识别“确认选择”按钮后执行确认三连击，不再检查勾选或重新扫描红色图标，避免鼠标遮挡导致卡住。按钮消失则安全返回等待，仍优先检查“再次进行”。

开启选卡后，原第一页“确认选择”模板在原 ROI 命中时，`CipherEndlessRewardPage` 不点击，先显式等待 1000ms 让奖励图标加载；等待结束后必须用新画面重新识别确认按钮和三个固定槽位，不能沿用等待前的结果。按 1→2→3 优先级取红色目标：命中第 1 张或完全未命中红色时直接确认；最左目标为第 2、3 张时点击该卡后直接确认。例如同时命中第 2、3 张仍选第 2 张，不依赖勾选状态。标题、编号、勾选及其模板文件均不再参与运行时识别。等待后确认按钮消失则不点击，返回可恢复轮询。每次重新进入奖励页门控都经过此等待；选卡后的直接确认不重复这段等待。1000ms 是仅针对奖励比按钮晚出现的业务等待，关闭开关时没有这段等待，三连击间隔仍为 50ms。该有限等待不保证任意慢加载或低对比度目标都可识别，仍需实机复测。

为排查选卡停顿，开启选卡时在运行日志输出 `[密函选卡]` 诊断：红色命中位置及三个分数、确认按钮分数和对应阈值，以及“最左红色在第 1 张，直接确认 / 点击第 N 张后直接确认，不检查勾选 / 未发现红色目标，允许确认默认奖励”的判断。不再显示标题、编号和勾选分数。位置与三项分数始终从左到右为 1/2/3；这是识别判断，不代表已经点击成功。只打印等待后 `ready` 节点实际识别的新画面，不打印等待前的红色结论或选卡候选的重复结果。判断变化时立即输出；同一判断的分数波动不刷屏，奖励页持续存在时每 10 秒更新一次。确认按钮未命中、模板缺失或画面格式错误也记录原因；相同的非奖励页等待不定时刷屏。去重仅保存在内存、任务变更重置，不缓存选择、不改变识别返回值、阈值、输入、计数或 Pipeline 时序；关闭选卡和其他模式不产生这些日志。

新增所有等待、选卡和确认后的状态均优先保留“再次进行”自然结束检测；奖励页残留或确认点击尚未生效时可重新检查并重试，进入“继续挑战”页时正常推进。选卡、直接确认、默认奖励回退和重试均不增加轮次；原来的第三页收尾仍是唯一的密函完整循环进度事件，99 轮提醒和 Telegram 完成通知不变。

参考截图保存在 `reference-screenshots/cipher-endless-reward-selection-d2fd94bd.png`，原图 `1294×730`，客户区 `(10,8,1280,720)`，包含游戏自绘标题栏，不缩放、不再扣除标题栏。`tools/extract_cipher_reward_templates.py` 可从原图复现红色方块模板；它生成的旧标题、编号和勾选模板仅保留作参考，不再用于运行时识别。原始客户区测试样本为 `tests/fixtures/cipher_reward_choice.png`。回归覆盖真实原图、全部八种红色槽位组合、不同勾选状态与鼠标遮挡不影响选卡后确认、标题/编号缺失或变化、亮暗场景背景、加载等待、页面残留、三连击时序和驱离隔离；合成样本不替代实机验证。

密函无尽每完成一整套三页流程累计 1 个局内轮次，首次累计到 99 时发送一次“局内 99 轮已完成”，任务与监控继续运行。若任一结算等待阶段识别到局外“再次进行”，则不点击该按钮、不增加新一轮，立即自然结束密函无尽任务；已开启进度监控时复用统一自然完成通知，向 Telegram 发送“密函无尽加速 / 无尽”任务已完成消息并停止监听。

#### 驱离

持续执行：

```text
等待战斗或结算
→ 可选：每个副本执行一次 E/Q 技能组合
→ 第一奖励页“确认选择”
→ “再次进行”
→ 第三奖励页“Space 确认选择”
→ 返回下一轮监控
```

密函驱离提供“副本轮次”设置，默认 1，范围 1–9999。轮次只在识别到“再次进行”时增加：记录第 N / 总轮数后，达到设定轮数就结束任务；未达到才点击“再次进行”和副本外 Space 确认进入下一轮。关闭“是否开启技能”时只处理结算、轮次和重新进入，不检测或释放角色技能。

局外状态并行轮询“再次进行”、副本外“Space 确认选择”和战斗血条。按钮仍存在时会重试；连续 3 帧检测到血条则直接切回局内。因此手动点击、自动跳过或偶发漏识别“Space 确认选择”不会让任务永久卡住。

识别到“再次进行”并完成轮次计数后，程序先三连击该按钮，再进入专用的重开等待状态。该状态可以重试仍残留的“再次进行”，但不会再次计数；随后持续识别并点击“Space 确认选择”，或在该页被跳过时通过连续 3 帧战斗血条直接进入下一轮。这样页面切换期间残留的“再次进行”不会被重复记录，也不会让任务卡在驱离结束后的“确认选择”。

### 普通无尽加速

#### 扼守

扼守按“副本轮次”运行，每轮代表一个完成后的 99 局副本。轮次只在识别到结算页的“再次进行”时增加：

```text
检测到“再次进行”
→ 记录已完成第 N / 总轮数
→ 达到总轮数：结束
→ 未达到：点击“再次进行”
→ 等待并点击“开始挑战”
→ 进入下一轮
```

任务启动、HUD 确认、技能释放和点击“开始挑战”均不会增加轮次。技能关闭时只处理局内“继续挑战”“确认选择”和局外重开；技能开启时，每轮战斗开始后额外执行一次 E/Q 组合。技能结束后仍在独立的局内监控中处理“继续挑战”和“确认选择”，但同一副本不会再次进入技能链。血条暂时消失后的边界未知阶段也继续轮询这两个合法局内按钮，避免按钮稍晚出现时漏识别。只有完成“再次进行”和“开始挑战”进入下一轮后才重新允许释放。无论技能是否开启，从“再次进行”页面启动任务都会先识别该页面并按完成轮次语义处理，不会卡在 HUD 等待。

“继续挑战”三连击后会立即进入过渡节点，优先检查并点击下一页的“确认选择”，不存在固定等待；若下一确认尚未出现，则马上恢复对应的局内监控。页面动画残影导致“继续挑战”被快速重试时，Agent 会忽略 5 秒内同一任务重复上报的局内轮次事件，因此不会重复增加 Telegram 进度。

技能关闭的主局内分支和技能释放后的局内分支使用完全相同的三节点快速点击结构；两条路径都不存在 Agent 内部 `repeat: 3` 慢速循环。

局外重开状态同时处理三种候选：“再次进行”仍存在则重试、“开始挑战”出现则点击、连续 3 帧检测到战斗血条则切回局内。因此即使按钮被手动点击、自动跳过或短暂漏识别，也不会留在“等待开始挑战”。

#### 无尽

仅监听并快速点击局内两个按钮：

- “继续挑战”：`(900, 500)`。
- “确认选择”：`(640, 505)`。

每次识别后点击 3 次，间隔 50ms。该模式不统计或限制局外副本轮次、不点击“再次进行”或“开始挑战”，也不提供角色技能设置；任务启动即代表当前局内第 1 局，之后按成功完成的“继续挑战”操作进入下一局，因此第 98 次成功推进后显示 99。局内轮次首次达到 99 时仍向手机发送一次“局内 99 轮已完成”，此时任务和监控继续运行，后续计数不会重复发送这条里程碑消息。

“继续挑战”点击后同样立即优先检查下一页“确认选择”，并对 5 秒内的重复进度事件去重，既保证连续确认能立刻处理，也避免按钮残影造成局内轮次虚增。

任务入口、局内按钮循环、空闲等待、“继续挑战”后的过渡和两个按钮三连击后的收尾状态，均优先检测“再次进行”。一旦识别成功，立即自然结束当前任务，不点击该按钮、不重开副本、不额外增加局内或局外轮次，也不要求当前进度必须达到 99。已开启进度监控时，复用与密函无尽相同的自然完成通知，向 Telegram 发送“普通无尽加速 / 无尽”任务已完成消息，然后停止监听；未开启监控时只结束任务，不启动通讯。三连击内部仍保持原来的三次原生点击和 50ms 间隔，完成无输入焦点收尾后检查终止信号。该检测仅在“普通无尽加速 → 无尽”启用，不改变普通扼守、普通驱离或其他任务的流程。

#### 驱离

局内不识别任何确认按钮；血条消失时只进入边界未知等待，同时优先等待血条恢复并观察局外专属按钮。只有识别到“再次进行”或“开始挑战”才确认已经进入局外；其中仍只有“再次进行”按与扼守相同的完成轮次语义计数。未达到总轮数时，依次点击“再次进行”和“开始挑战”进入下一轮。

普通驱离的“副本轮次”默认 1，允许设置 1–9999，与密函驱离的上限一致。

技能关闭时只进行血条状态分区以及局外结算与重开；技能开启时，每个副本只执行一次 E/Q 组合，之后进入保留技能锁的局内/局外监控，不会因血条重新出现而在同一副本重复释放。点击“开始挑战”进入下一轮后才重新允许释放。两种状态都支持直接从“再次进行”页面启动。

普通驱离与扼守共用上述可恢复的重开等待逻辑。

### 皎皎币挂机

“皎皎币挂机”是“日常挂机”分组下的独立任务。任务入口不会从局内、结算页或任意其他页面接管，只持续等待用户指定委托页面右下角的“开始挑战”；识别成功后依次点击该按钮和弹窗内的 `Space 开始挑战`。

进入副本后先连续 3 帧确认角色血条，再在 1500ms 窗口内识别指定小地图：

- 命中目标小地图：先等待 3000ms 让战斗输入层稳定，再执行固定角色操作 `E → 等待 300ms → E → 等待 300ms → S 600ms → Q → 等待 3500ms → S 5000ms → D 100ms`，然后复用普通扼守的“继续挑战 → 确认选择”局内加速逻辑，直至当前副本完成 99 局。`S 600ms`、`S 5000ms` 和末尾 `D 100ms` 均表示按住对应按键后再释放；整套按键只建立一次焦点恢复上下文，全部完成后才切回用户窗口。
- 未命中目标小地图：依次发送 `Esc`、点击“放弃挑战”、点击“确定”，等待局外“再次进行”并重新进入。主动放弃只代表地图不符合要求，不增加已完成副本轮次。

识别到“再次进行”时即把局外副本轮次增加 1；正常 `99 / 99` 直接记录完成，提前结算则按上文保留真实进度并发送一次异常通知。未达到设置总数时执行：

```text
再次进行
→ 弹窗 Space 开始挑战
→ 连续确认战斗 HUD
→ 检查目标小地图
→ 执行固定角色操作并开始下一副本的局内循环
```

副本轮次默认 1，范围 1–999。局内轮次和局外副本轮次与普通扼守含义相同；点击两个“开始挑战”、错误地图放弃重试和固定角色操作都不会增加局外完成数。

正常重开时，“再次进行”后直接优先识别并点击 Space“开始挑战”。Space 点击后的战斗加载监控会优先连续确认血条；加载期间若仍看到旧委托页“开始挑战”，必须等待 1500ms 并再次确认该按钮持续存在，才允许按真实返回委托页处理，避免页面残影把状态机带回局外。即使 Space 页面被手动点击、自动跳过或先前已经误入等待 Space 状态，该等待状态也会通过连续三帧血条直接恢复到小地图检查和局内流程。如果游戏确实返回委托列表或委托详情页，同一个重开监控仍会依次恢复处理“扼守/无尽”委托卡片和委托页“开始挑战”，之后回到 Space“开始挑战”再进入局内。

皎皎币挂机的所有三连鼠标操作都与普通扼守使用同一组三段快速点击，包括委托页“开始挑战”、弹窗 `Space 开始挑战`、异常返回时的委托卡片、“再次进行”、局内“继续挑战 / 确认选择”以及错误地图的“放弃挑战 / 确定”。三次全部为 Maa 原生点击，前两次间隔 50ms；第三次点击后进入不发送输入的 Agent 收尾节点恢复焦点，并只记录一次逻辑进度。因此这些按钮既不会走 Agent 内部慢速重复路径，也不会让 Agent 鼠标输入误触发角色攻击。

### 调停挂机

“调停挂机”是“日常挂机”分组下的独立任务，并作为默认关闭项加入“普通挂机”预设。不要与普通无尽同时启用：长期任务按队列顺序执行，排在前面的任务会阻塞后面的任务。

任务入口与其他有限副本一致，先按未知状态并行分类：优先识别结算页“再次进行”，也识别弹窗内的 `Space 开始挑战` 和已经出现的战斗血条；仍不识别委托页“开始挑战”，也不检查皎皎币目标小地图。从“再次进行”页面启动时，该页面代表一个已经完成的副本，因此立即计入一轮；若设置总数为 1，则直接结束，不再点击重开。点击弹窗或直接接管局内后连续 3 帧确认角色血条，确认进入局内后先等待 3000ms，让战斗输入层稳定，再执行以下固定前台角色操作：

```text
W 按下
→ 等待 1500ms
→ W 抬起
→ 左键按下
→ 等待 250ms
→ 左键抬起
→ 等待 300ms
→ F
→ 等待 300ms
→ F
→ 等待 300ms
→ F
→ 等待 300ms
→ F
→ 等待 800ms
→ 鼠标一次性向上移动 130px
→ 等待 500ms
→ 右键按下
→ 等待 800ms
→ 右键抬起
→ 等待 800ms
→ Z
```

W 按下后持续保持 1500ms 再抬起，然后按住左键 250ms 并抬起。等待 300ms 后发送第一次完整 F，之后以 300ms 间隔继续发送三次完整 F；第四次 F 后等待 800ms，接着重新确认游戏拥有前台焦点，以一次 Windows 物理相对鼠标事件向上移动 130px，等待 500ms 后按住右键 800ms，抬起后等待 800ms，再发送一次完整 Z。玩法鼠标输入不使用 Maa 的 `post_relative_move / post_touch_*`，因为控制器返回成功只代表事件已提交，实测游戏不会消费这组事件。该序列不发送 Shift。整组输入完成后额外保留游戏前台 500ms，再恢复用户原窗口和鼠标；若 W、左键或右键抬起失败，Agent 会在恢复焦点前再次兜底抬起，避免角色持续移动或鼠标按键卡住。

每次整组输入成功后只输出一条结果日志，并在该行完整打印 `W↓ → 1500ms → W↑ → 左键↓ → 250ms → 左键↑ → 300ms → F → 300ms → F → 300ms → F → 300ms → F → 800ms → 鼠标瞬时↑130px → 500ms → 右键↓ → 800ms → 右键↑ → 800ms → Z`，用于直接核对实际执行序列，不为每个按下、等待和抬起步骤分别刷屏。

局内不识别“继续挑战”或“确认选择”，只维持血条状态边界并等待局外专属“再次进行”。识别到“再次进行”才把局外副本轮次增加 1；达到用户设置的总数就结束，否则执行：

```text
再次进行
→ 弹窗 Space 开始挑战
→ 连续 3 帧确认战斗 HUD
→ 等待 3000ms
→ 执行固定 W/左键/四 F/鼠标/右键/Z 角色操作
→ 等待下一次再次进行
```

“再次进行”和弹窗 `Space 开始挑战` 都使用三次 Maa 原生鼠标点击，前两次间隔 50ms，第三次后通过无输入收尾节点恢复焦点。重开等待会同时检查残留“再次进行”、Space 开始页和已经出现的战斗血条，因此手动处理或偶发漏识别中间页面后仍能恢复。副本轮次默认 1、范围 1–9999；调停没有局内 99 轮进度，Telegram 状态只显示已完成的局外副本轮次。

### 狩月人之阶挂机

“狩月人之阶挂机”是“日常挂机”分组下的活动副本任务，并作为默认关闭项加入“普通挂机”预设。任务可从结算页或已经进入的副本接管，不识别调停挂机的 Space“开始挑战”页面，也不识别任何局内确认按钮。

局内沿用有限副本的血条边界：连续 3 帧确认战斗 HUD 后等待 3000ms，再以一个连续的前台输入组执行三次 `左键↓ → 300ms → 左键↑ → 等待 300ms`。第三次的常规等待结束后再额外等待 300ms，因此第三次左键抬起到 Q 共等待 600ms；随后执行 `Q → 3500ms`。起手完成后，每隔 300ms 发送一次 E。每次 E 前都优先识别局外专属“重新开始”，所以只有该按钮出现才停止循环，血条在 Q 动画或战斗表现中暂时消失不会中断输入。同一副本不会因血条恢复而重新执行起手动作。

局外唯一完成证据是活动结算页左下角的“重新开始”。识别到该按钮后先结束本副本共享输入组并恢复用户原窗口和鼠标，再把局外副本轮次增加 1；达到设定次数时直接结束，未达到时在 `(540, 630)` 使用三次 Maa 原生点击，前两次间隔 50ms，第三次后恢复焦点并直接等待下一副本血条。重开后不等待任何 Space 开始页；若“重新开始”仍残留则重试同一快速点击链，但不会重复计数。

```text
结算页“重新开始”
→ 记录已完成第 N / 总轮数
→ 未达到总轮数：三次快速点击“重新开始”
→ 连续 3 帧确认战斗 HUD
→ 等待 3000ms
→ 连续三次：左键按住 300ms 后抬起，再等待 300ms
→ 额外等待 300ms
→ Q
→ 等待 3500ms
→ 每 300ms 发送一次 E，并在每次 E 前检查“重新开始”
→ 命中“重新开始”后停止 E 循环并恢复焦点
```

副本轮次默认 1，范围 1–9999。Telegram 只显示已完成的局外副本轮次与配置总数，不显示局内轮次。

### 沉浸式戏剧挂机

“沉浸式戏剧挂机”是“日常挂机”分组下的独立 `Win32-Foreground` 任务，并作为“普通挂机”预设中的默认关闭项。用于按钮实测的全局“前往”检测已撤回：任务入口和首次血条确认不扫描“前往”，首次需手动进入副本；三帧血条确认后才执行角色方案。不检测小地图、错误地图、高台或任何局内“继续挑战 / 确认选择”。

“角色方案”提供默认的“伊薇”（内部标识 `CoinDefault`，兼容已保存配置）与“伊薇（不持续 E）”（`YiweiNoE`）。两者使用完全相同的戏剧独立 W/D/F/Q 起手及全部时间参数，**不执行复制来的皎皎币操作**；只在 Q 后是否持续按 E 上不同，皎皎币及其他任务不受影响。默认“伊薇”流程保持不变：

```text
连续 3 帧确认角色血条
→ 等待 3000ms
→ W 按住 1000ms 后抬起
→ D 按住 1000ms 后抬起
→ F → 200ms → F → 200ms → F
→ Q 一次 → 等待 1000ms
→ 循环：先检测“前往”，未命中才按 E 一次，再等待 500ms
→ “前往”命中：停止 E，原生点击 → 50ms → 原生点击 → 50ms → 原生点击
→ 无输入收尾：关闭本副本连续输入组、恢复窗口和鼠标、记录一次成功日志
→ 前往残留则重试；否则等待下一副本连续三帧血条，再执行选定角色方案
```

“伊薇（不持续 E）”保留上述完整起手，随后不发送任何 E，进入 `SceneMonitor2` 并依次识别第 2 至第 5 试炼；每次识别后等待 3000ms，再左键长按 300ms，最终转入 `InsideMonitor` 或下一副本等待。每个场景只成功一次，三帧 HUD 门控、起手锁和 `Go` 优先级保持不变；血条暂时消失或恢复不会重放起手。两个 case 显式选择对应动作路由，切回“伊薇”会恢复持续 E。

不持续 E 方案在每个副本的起手后进入单调 Pipeline 场景图：每个监控节点先检查“前往”，再尝试当前及更高编号场景。命中候选后固定等待 3000ms，再复用既有输入组左键长按 300ms 一次；完成后转入下一编号监控或局内监控。等待期间不并发轮询“前往”，只在延迟结束后优先检查；每个场景最多成功一次，缺失早期场景时不回放，未知场景不记录日志、不发送输入。默认“伊薇”分支仍保持原持续 E 路由。

最终试炼只直接匹配提供截图中的完整满血 Boss 条 `TheatreAFK/scene5.png`：在 `(390,60,520,50)` ROI 内保留原始颜色与全部填充，使用 `TM_SQDIFF_NORMED ≤ 0.05`，不再使用红色区域、外框遮罩或残血兼容检测，避免将前四个场景的普通红色进度条当作最终试炼。按首次出现时满血的条件识别；第二、三、四试炼文字检测、每场一次限制及 `3000ms → 左键 300ms` 不变。回归覆盖原始满血截图及合成相似进度条；实际误识别进度条尚无截图样本，仍需实机复测。

场景左键动作复用已有前台输入组：确认游戏前台后发送真实左键按下/抬起，不额外移动鼠标，不发送后台鼠标消息。该左键是局内角色操作；“前往”仍使用 Maa 原生三连击。

W、D 顺序长按，不同时按住；F 只有两段 200ms 间隔，第三次 F 后直接 Q。Q 在此方案中只发送一次。默认“伊薇”每次 E 后的 500ms 由 Pipeline 显式控制，不在 Agent 中运行无限循环；其日志只打印完整起手结果、循环开始和局外点击成功，不以每秒两条 E 日志持续刷屏。“伊薇（不持续 E）”则为每个已识别场景和对应左键完成各记录一次。两种方案的血条暂时消失或恢复都不会重放 W/D/F/Q 起手；完整操作固定共用一个前台输入组，手动停止或任务失败同样关闭本任务的输入组。

“前往”模板为 `TheatreAFK/go.png`，只裁取固定文字，不包含变化的幕数、阵容或场景。提供的原图为 `1327×756`，其中游戏窗口区域为 `(29,16,1280,720)`；游戏自己绘制的标题栏属于这个客户区，不能再扣除 30px。按 `1280×720` 窗口基准，文字裁剪为 `(1150,662,46,25)`，识别 ROI 为 `(1080,640,190,65)`，匹配阈值 `0.85`，三次点击均为 `(1172,673)`。后两次使用 `DirectHit + Click`，第三次后以 `0ms` 进入无输入 `focus_guard_finalize`，启用本任务专用的 `finish_skill_input_group` 收尾，沿用现有 100ms 恢复等待；Agent 不执行页面点击。重开等待仍为 `0 / 0 / 50`，E 循环路由为 `0 / 0 / 0`，仅 E 节点的 `post_delay` 为 500ms，不叠加隐藏等待。

两个角色方案的“全程后台输入（实验）”开关已删除。起手 W/D/F/Q、伊薇的持续 E，以及不持续 E 方案的换场景左键，均固定使用前台真实输入。保留全部动作与时间参数、每副本一次的起手锁和连续输入组；只在“前往”收尾、手动停止或失败时恢复用户窗口与鼠标，不在每个按键之间反复恢复。

旧配置即使残留后台动作入口，也只会转到相同的前台序列，不能重新启用剧场后台控制。剧场不使用驱离、钓鱼的后台就绪状态；其他任务后台功能不变。前台恢复仍是尽力执行机制，可能受 Windows 限制。

下一副本等待及前两帧血条确认的候选优先处理残留“前往”，避免按钮尚在时把 HUD 当成新的开局。失败的血条确认退回同一个重开等待，不回到任务初始化。此模式不提供轮次设置或进度计数；共享状态的 total/stage_total 只在任务开始时初始化为 0，按钮重试不计数、不重复发送启动通知。不同角色方案独立选择动作路由和日志，共用入场门控；每个副本只执行一次起手，之后按所选方案重复 E 或保持无输入等待，直到确认“前往”。

当前只授权“前往”，没有最终完成检测，也不会点击“返回”或其他未知按钮。点击后若既没有“前往”也没有血条，就持续安全等待并支持手动停止，不伪造完成。若卡在中间页面，请提供**点击“前往”后停留页面的完整游戏窗口截图**（保持 `1280×720`，包含按钮文字）；也可手动处理该页，三帧血条出现后会继续。未被助手观察到“前往”就手动跳入另一副本，不会自行解锁，需停止再启动任务。

### 钓鱼挂机

“钓鱼挂机”是“日常挂机”分组下的独立长期任务，与任何副本、局内外状态、血条和轮次计数无关。使用前由用户自行站在大世界钓鱼地点并进入可钓鱼状态；任务持续扫描完整 `1280×720` 游戏画面：

任务选项“钓鱼数量”范围为 `1–9999`，默认 `120`。只有成功发送 Esc 关闭一次钓鱼结算提示后才把数量加 1，代表完整钓到 1 条鱼；Space 和 E 只推进钓鱼流程，不计数。达到设定数量的那次 Esc 仍完整执行，随后任务立即成功结束，并触发现有的 Telegram 任务完成通知。若画面出现“水中暂时无鱼”，任务会优先识别该文字并立即自然结束，不发送额外游戏按键；已记录的钓鱼数量保持不变，Telegram 只发送“鱼池已空。”。

```text
识别到鱼竿图标且 Space 锁已到期 → 成功发送一次 Space → 不增加数量
识别到鱼形收鱼图标且 E 锁已到期 → 成功发送一次 E → 不增加数量
识别到“点击空白区域关闭”且 Esc 锁已到期 → 等待 500ms → 成功发送一次 Esc → 钓鱼数量 +1
每次接受一个提示后 → 仅锁定该提示 3000ms
3000ms 到期后提示仍存在 → 再次接受并发送对应按键
识别到“水中暂时无鱼” → 记录鱼池为空 → 立即成功结束任务
```

鱼竿和鱼形模板虽然带有场景背景，但自定义识别器不会直接匹配棕色背景。它会把模板和实时画面都转换为“亮度至少 175、饱和度至多 115”的白色 HUD 轮廓掩码，只使用鱼竿、鱼钩和鱼形轮廓进行归一化相关匹配，固定阈值均为 `0.72`。“点击空白区域关闭”仍使用灰度 Canny 字形边缘匹配，阈值 `0.65`；这三个可操作提示仍采用全屏识别。

“水中暂时无鱼”单独使用抗背景文字检测：只搜索 `1280×720` 基准下中上方提示条范围 `[320, 180, 640, 140]`（x、y、宽、高），先用 `5×5` 灰度白顶帽去除局部背景亮度、保留细文字笔画与抗锯齿，再匹配预缓存的 `95%、97.5%、100%、102.5%、105%` 五种模板尺寸。整句相关分数至少 `0.85`，并且按顺序分成三段的字形分数都至少 `0.80` 才能命中，降低部分文字相似造成误结束的风险。只匹配固定的“水中暂时无鱼”，不包含后面的刷新时间；不得退回全屏降低阈值的方案。该检测使用用户提供的冰雪地图漏识别截图做回归，并覆盖合成背景、淡化、微缩放、缺字和无提示负样本；仍需在更多地图实测，不保证任意字号、遮挡或极低对比度都能识别。

可操作的 `Space`、`E`、`Esc` 分别维护独立的 3000ms 时间锁，一种提示的触发不会锁住另外两种。“水中暂时无鱼”始终排在候选首位，命中后直接结束，因此不需要重试输入。锁定使用单调时钟，不再要求提示消失，也不受系统时间调整影响。鱼池耗尽不会增加钓鱼数量、发送额外按键或改变原有前台/后台输入规则。

默认情况下，Space、E、Esc 每次都使用前台真实输入，并在结束后尝试恢复用户原窗口和鼠标；关闭文字命中后会先等待固定 500ms 再发送 Esc，Space 和 E 不增加这段等待。三个按键共用一个“首次前台触发，后续后台发送（实验）”开关，默认关闭；开启后，本任务第一次实际按键使用前台真实输入，成功后同一任务后续 Space、E、Esc 全部使用同一套 `PostMessageW` 后台状态。重新开始任务会重置为首次前台。无论前台还是后台，只有 Esc 发送成功才把“钓鱼数量”增加 1；Space 和 E 不计数，各提示在自己的 3000ms 时间锁内也不会重复触发。后台投递成功只证明 Windows 接受消息，不能证明游戏输入层一定消费。

钓鱼的用户日志只在任务启动和实际输入成功后记录，不输出“已识别、准备发送”或独立的“后台窗口消息已发送”过程行。启动时显示 `钓鱼数量：0 / 目标`；Space/E 成功时只显示按键与前台/后台方式，不显示或增加计数；每次 Esc 成功并完成计数后，将按键、方式和更新后的 `当前数量 / 目标数量` 合并为一行。达到目标时额外显示包含最终数量的任务完成行。异常与输入失败日志不受精简规则影响。

## 角色技能规则

角色技能适用于：

- 密函驱离。
- 普通扼守。
- 普通驱离。

共同规则：

1. 连续 3 帧识别左下角角色血条，确认战斗 HUD 已就绪。血条背景不透明，比透明背景的 Q 图标稳定。
2. 所有“等待时间（ms）”输入项默认均为 3000ms；技能触发延迟允许的最小值仍是 2000ms。
3. 按开关执行 E 和 Q。E 默认 2 次；密函驱离和普通驱离的默认 E 间隔为 1000ms，普通扼守为 1250ms。连续 E 仍由 Maa 的显式 `repeat / repeat_delay` 控制次数和间隔，但每次 E 都复用同一个技能输入组，不会逐次退出焦点保护；间隔选项不得覆盖 E 动作所需的完整 Agent 参数。
4. Q 图标不再参与战斗开始或技能触发判断；Q 是否释放只由选项开关决定。每次释放会连续发送 3 次 Q，间隔 100ms，确保游戏收到输入。Q 与同一副本的全部 E 属于同一个连续输入组，不会在 E/Q 之间恢复用户窗口。
5. 只有 E、Q 都开启时才显示“Q 在 E 前释放”。关闭时执行 `E 连点 → 等待 E 间隔 → Q`；开启时显示独立的“Q 后触发间隔”，其“等待时间（ms）”默认同样为 3000ms，并执行 `Q → 等待 Q 后触发间隔 → E 连点`，最后一个 E 后不再等待。
6. 技能组合结束后进入结算监控，同一副本不重复释放。
7. “首次副本前台，后续副本后台”只提供给密函驱离和普通驱离，默认关闭；普通扼守固定使用默认前台技能输入。前台技能组只在第一项实际 E/Q 前记录用户窗口与鼠标并切入游戏，E 连点、E/Q 间隔和 Q 三连全部完成、走到 `LiseSkillCastEnd` 后才恢复一次。驱离开启实验项后，每个新任务的首个副本整组前台发送；下一副本及后续副本整组使用 Windows 后台窗口消息，不能在同一技能组的 E 与 Q 之间切换输入方式。若 Windows 明确拒绝后台消息，本组自动改用前台真实按键，直到公共出口才恢复焦点；成功完成后，下一副本重新允许后台模式。其他按钮点击始终使用原有焦点恢复机制。后台日志成功仍只能确认 Windows 接受消息，不能证明游戏输入层一定消费。

释放 Q 期间血条可能临时消失。此时程序只进入保留技能锁的边界未知等待，不会把血条消失当成副本结束；血条恢复后继续局内监控，识别到局外专属按钮后才进入局外流程。

每次 E 连续点击都会单独记录日志，例如 `[角色] E 连续点击：第 1 / 2 次已发送`，便于确认设定次数是否全部执行。

密函驱离和普通驱离还提供“仅高台释放 E”：

- 关闭：等待配置延迟后，按 E/Q 开关直接执行。
- 开启：连续确认 HUD 后立即在 300ms 窗口内锁定高台或非高台结果，再等待完整配置延迟。
- 高台：按配置执行 E 和 Q。
- 非高台：跳过 E，若 Q 已开启则执行 Q。

普通驱离开启“仅高台释放 E”时，首次入场和“再次进行”后的入场都会在连续 3 帧血条确认后直接进入高台判断入口；此时不会经过已禁用的普通技能延迟节点。关闭高台判断时，两条入场路径恢复为先进入普通技能延迟。密函驱离通过 `CipherExpelCombatEntry` 的备用入口完成同样分流。

普通扼守没有高台判断选项。

## 焦点恢复

控制器默认执行真实前台输入。Python Agent 会持续记录用户正在操作的非游戏窗口及鼠标屏幕坐标；页面点击的三次游戏输入全部由 Maa 原生节点完成，随后由无输入的 `focus_guard_finalize` 先释放鼠标限制，再尝试切回原窗口，并在窗口恢复成功时把鼠标移回记录位置。坐标使用 Windows 虚拟屏幕坐标，因此支持位于主屏左侧或上方的显示器负坐标。如果任务启动时游戏本来就是前台窗口，必须清除上一次任务遗留的非游戏恢复目标；E/Q、钓鱼和角色操作集开始输入时若游戏仍是前台，也必须保持游戏前台，仅释放鼠标限制，不得切换到历史窗口。三个技能功能都把一套 E/Q 视为单个焦点生命周期：首个实际按键前最多切入游戏一次，连续 E、Q 三连及它们之间的业务等待期间保持同一种输入方式，公共出口只恢复一次。调停的完整录制序列也使用单个焦点生命周期：W、F、Z 通过 Maa 控制器的键盘接口发送；左键、相对移动和右键蓄力使用游戏前台下的 Windows 物理鼠标事件，并在每项玩法鼠标输入开始前再次确认前台。Z 完成且保留 500ms 后才恢复原窗口和原鼠标位置。密函驱离和普通驱离开启实验后台输入后，仅下一副本及后续副本的完整 E/Q 组不切换窗口；普通扼守的完整技能组始终使用前台真实输入。

这是尽力恢复机制，不是强保证：Windows 可能拒绝前台切换，临时弹窗也可能改变候选窗口。只有原窗口仍有效且成功恢复时才移动鼠标，避免游戏仍在前台时把鼠标意外拉走。当前自定义动作只以游戏输入是否成功作为最终成功状态，窗口或鼠标恢复失败不会使任务失败。

## 手机查询当前进度

“进度监控”任务负责启动 Telegram Bot。仅仅打开 UI 不会启动监听。每次新监听启动时先用零超时读取 Telegram 当前积压更新，以最大 `update_id + 1` 建立本次基线，并丢弃监听启动前发送的所有旧命令；因此离线期间发送的旧 `disconnect` 不会在下次启动时关闭新监听。单独运行时任务会持续保持运行，UI 的“结束任务”按钮和 `F11` 始终可用，并向手机发送“监控已开启 / 无任务”；停止后关闭 Telegram。若它后面排有受支持的游戏任务，Agent 会从 MXU 当前日志的已提交任务映射中确认队列并自动作为一次性启动器，启动后台监听后立即让位，不发送“无任务”，而由游戏任务发送正式任务名和模式。监控启动满 30 分钟后自动发送一次与 `/status` 相同的当前状态，此后每 30 分钟继续发送。配置的手机账号也可以随时发送 `/status` 或“进度”，立即查询当前状态、运行时间和更新时间；监听已启动后发送的 `disconnect` 或 `/disconnect` 会先收到确认并消费该条 Telegram 更新，再发布与设置按钮相同的全局停止信号，并关闭本实例的接收、发送、定时状态和所有权线程。发出命令的实例成功停止后，助手日志必须显示 `[进度监控] disconnect 已执行，本机全部监控通讯已关闭；当前任务继续运行`；其他当前版本 Agent 会在最多约 2 秒内响应同一信号并记录收到全局关闭通讯信号。当前游戏自动化任务、AgentServer、共享任务进度、游戏及 DNA Helper 窗口均继续运行；需要远程恢复通讯时，停止并重新开始带“进度监控”的任务即可。

手机状态沿用上文的轮次定义：

- 密函无尽、普通无尽：显示已完成的局内轮次。
- 普通扼守：同时显示局外副本轮次（已完成）和当前副本内的 `/99` 局内轮次。
- 普通驱离、密函驱离：显示局外副本轮次（已完成）与配置总数。
- 皎皎币挂机：显示局外副本轮次（已完成）以及当前副本的 `/99` 局内轮次。
- 调停挂机：只显示局外副本轮次（已完成）与配置总数，不显示局内轮次。
- 狩月人之阶挂机：只显示局外副本轮次（已完成）与配置总数，不显示局内轮次。
- 沉浸式戏剧挂机：只显示运行状态、运行时间和更新时间，不显示任何轮次或计数。
- 钓鱼挂机：显示运行状态、已成功发送 Esc 完成结算的钓鱼数量与设定目标、已运行时间，不显示任何副本轮次。

局内入场和“继续挑战”、密函完整结算循环等逻辑事件成功后只累计一次，不会按三次物理点击重复计数。普通扼守与皎皎币的结算记录保留真实局内进度，绝不在“再次进行”出现时强制写成 `99 / 99`；局外副本轮次仍只由“再次进行”触发的原有轮次日志更新，Telegram 不建立第二套业务计数。普通无尽和密函无尽的局内计数首次达到 99 时发送一次“局内 99 轮已完成”，任务与监控保持运行；第 100 轮及以后不重复发送。两种无尽模式一旦识别到“再次进行”便自然结束，不额外增加轮次，并通过任务成功事件发送对应任务和“无尽”模式的 Telegram 完成通知，随后停止监听。密函无尽循环会再次经过任务入口，但初始化按同一个 Maa `task_id` 去重，同一任务只发送一次启动通知。

Telegram 接收轮询、消息发送和 30 分钟定时调度分别使用后台线程；定时线程只读取共享状态并放入发送队列，不修改轮次。单独的所有权守护线程是唯一允许刷新监听权文件的线程，其他工作线程只响应同一个停止事件，避免并发读写锁文件让 `/status` 接收或定时发送线程意外退出。守护线程每 2 秒同时检查全局通讯停止代次，并会容忍两次瞬时监听权刷新失败；连续三次失败只以 `reset_progress=False` 停止当前旧实例的 Telegram 通讯，不得关闭 AgentServer、当前游戏任务或重置进度。`disconnect` 只接受配置中的 `allowed_chat_id`；处理时必须同步发送确认消息，再用 `update_id + 1` 进行一次最终 `getUpdates` 确认，避免重启后反复执行同一条关闭命令，随后广播新代次并以 `reset_progress=False` 关闭 Telegram 全部线程。严禁保存自定义动作中的临时 `Context.tasker` 并从 Telegram 线程调用：该反向接口在动作返回后失效，会抛出 `OSError`。确认、更新消费或广播失败也必须至少关闭当前实例，错误日志不得包含 Bot Token。断网、超时和重试不会阻塞游戏点击或技能操作；配置缺失、损坏或启动异常时，“进度监控”记录“已跳过”，队列中的后续游戏任务仍会运行。

监控受 UI 任务生命周期约束：执行内置预设时，游戏任务自然成功会向手机发送“任务已完成”，其中包含正式任务名和模式，然后停止 Telegram 轮询、发送和定时线程；调停挂机、狩月人之阶挂机与其他有限副本任务使用相同的自然完成通知，钓鱼挂机因“水中暂时无鱼”自然结束时改为只发送“鱼池已空。”。点击“停止任务”/按 `F11` 或任务失败时只停止监听，不误报完成。独立监控被手动停止时也只关闭监听。停止会清除尚未发送的普通队列消息；自然完成通知由独立的一次性后台发送器投递，不会被该清理吞掉，也不会阻塞 Maa 任务结束。只有实际运行的监听被关闭时才记录“监听已停止”；未选择监控时结束普通任务不会产生这条日志。若手动创建“监控＋游戏任务”的自定义队列，只需把监控放在最前；Agent 只读取 MXU 已写入的当前任务提交映射，不会查询不存在的 Maa 任务 ID。

Python Agent 还会持有启动它的 UI/MXU 父进程句柄并等待父进程结束。若任务仍在运行时从托盘右键退出 UI，或者 UI 崩溃、重启而没有产生正常任务停止事件，Agent 会立即停止 Telegram 并关闭自身，不发送“任务完成”，避免孤立 Agent 持续发送旧进度。若 MaaFramework 未在 5 秒宽限期内正常退出，Agent 会强制结束自身；不会结束游戏或新的 Helper。只有父进程退出才走这条完整 Agent 关闭路径；新 Agent 接管 Telegram 监听权时，旧 Agent 只停止自身的接收、发送、定时状态和所有权线程，其当前游戏任务继续运行。父进程监控绑定的是具体进程句柄，不依赖可能被 Windows 复用的 PID。

先在 Telegram 中通过 `@BotFather` 创建 Bot，并向新 Bot 发送 `/start`，然后在项目目录运行：

```powershell
python tools\configure_telegram.py
```

按提示粘贴 Bot Token。Token 输入时不会显示；如果桌面版已经构建，脚本写入 `dist/DNAHelper/config/telegram.json`，否则写入项目的 `config/telegram.json`。`config/` 已被 Git 忽略，不得提交或公开 Token。配置完成后可以启动内置挂机预设，也可以单独运行“进度监控”；仅重启 DNA Helper 不会启动监听。电脑必须保持联网并能访问 `api.telegram.org`。Bot 只响应配置中的 Chat ID，其他账号的消息会被忽略。

如需手动配置，可复制 `config.example/telegram.json`：源码运行时放到项目的 `config/telegram.json`，桌面版放到 `dist/DNAHelper/config/telegram.json`。

## 验证

每次修改任务、选项、Pipeline 或模板后至少运行：

```powershell
python tools\validate_project.py
python -m compileall -q agent tools
python -m unittest discover -s tests -v
```

校验器当前检查：

- 接口导入、任务分组、中文标题和说明。
- 选项引用与预设任务引用。
- Pipeline 节点重名、任务入口、`next` / `on_error` 悬空引用。
- 全部 Pipeline 节点显式声明非负的 `rate_limit`、`pre_delay`、`post_delay`，拒绝继承框架默认时序。
- `pipeline_override` 目标。
- Agent 动态调用的 Pipeline 目标。
- 所有当前节点是否至少在一个任务、选项或 Agent 动态路径中可达。
- 模板文件是否存在。
- Agent 进程 marker 与监控通讯停止信号的固定 schema、启停生命周期、Telegram 只广播不终止的边界，以及定制 MXU 本地孤立 Agent 身份核验、扫描清理结果、中文按钮与全部 locale 键。修改本地清理时还须执行 Rust `process_control` 测试，覆盖正常父进程保留、PID/路径不符、未知父进程、测试专用孤立进程的真实终止及退出确认；不得拿用户运行中的 Agent 做破坏性测试。

## 当前已知限制

- 桌面版尚未强制检查 `1280×720`。
- 长期监控使用 `max_hit: 1000000000`，并非数学意义上的无限。
- 正常的非高台和部分 HUD 等待仍通过错误分支表达，可能持续生成 `debug/on_error` 截图。
- 构建过程不是事务式的。
- 焦点恢复失败不会反馈为任务失败。
- 桌面目录依赖系统 Python 和已安装的 `maa` 包，不是真正独立发行包。

详细状态见 [2026-08-11 审计报告](docs/audit-2026-08-11.md)。
